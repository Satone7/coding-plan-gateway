# Feature Specification: Docker Auto-Update

**Feature Branch**: `016-docker-auto-update`  
**Created**: 2026-03-31  
**Status**: Draft  
**Input**: User description: "给生产环境的Dockerfile生成的镜像，提供自动获取更新的功能，启动时检查master分支是否有更新，如果有则拉取最新的代码，然后重新编译再启动服务"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Automatic Update Detection and Application (Priority: P1)

作为运维人员，当我部署一个启用了自动更新功能的 Docker 容器时，我希望容器在启动时自动检查是否有新代码可用，如果有则拉取最新代码、重新编译并启动服务，这样我就不需要手动登录服务器来更新代码。

**Why this priority**: 这是该功能的核心价值——减少手动运维工作，确保生产环境始终运行最新代码。没有这个能力，用户仍需手动管理部署。

**Independent Test**: 可以通过在本地 Docker 环境中测试：1) 构建启用了自动更新的镜像；2) 启动容器时指定一个测试分支；3) 验证容器启动日志显示检查更新、拉取代码、重新编译、启动服务的完整流程。

**Acceptance Scenarios**:

1. **Given** 容器配置了自动更新且 master 分支有新提交，**When** 容器启动时，**Then** 系统应检测到有更新、拉取最新代码、重新编译并启动服务
2. **Given** 容器配置了自动更新且 master 分支没有新提交，**When** 容器启动时，**Then** 系统应直接使用现有代码启动服务（无需重新编译）

---

### User Story 2 - Manual Update Trigger (Priority: P2)

作为运维人员，我希望能够在容器运行期间手动触发更新检查，而不仅限于启动时，这样当紧急修复发布时我可以立即应用更新而无需重启容器。

**Why this priority**: 这个功能提供了额外的灵活性，允许运维人员在运行时主动触发更新。虽然不是核心功能，但对于需要快速响应的场景很有价值。

**Independent Test**: 可以通过向运行中的容器发送信号或调用特定端点来触发更新，然后验证更新流程被执行并记录日志。

**Acceptance Scenarios**:

1. **Given** 容器正在运行且 master 分支有新提交，**When** 运维人员手动触发更新，**Then** 系统应执行完整的拉取-编译-重启流程

---

### User Story 3 - Update Failure Handling (Priority: P3)

作为运维人员，我希望当自动更新失败时（如网络问题、编译错误），系统能够优雅地回退到使用现有代码启动，并记录错误日志，这样即使更新失败，服务仍然可用。

**Why this priority**: 错误处理对于生产环境至关重要，确保即使自动更新失败也不会导致服务不可用。这是一个重要的可靠性保障，但不是核心功能。

**Independent Test**: 可以通过模拟网络中断或引入编译错误来测试错误处理逻辑，验证系统能够正确回退并记录错误。

**Acceptance Scenarios**:

1. **Given** 自动更新过程中发生网络中断，**When** 拉取代码失败时，**Then** 系统应使用现有代码启动服务并记录网络错误
2. **Given** 代码拉取成功但编译失败，**When** 编译过程出错时，**Then** 系统应使用上一次成功编译的版本启动并记录编译错误

---

### Edge Cases

- **网络不可用**: 容器启动时无法连接到 Git 仓库，系统应直接使用现有代码启动，不阻塞服务
- **Git 仓库认证失败**: 配置的凭证无效或过期，系统应记录认证错误并使用现有代码启动
- **磁盘空间不足**: 拉取或编译过程中磁盘空间耗尽，系统应清理临时文件并回退到现有代码
- **并发更新冲突**: 多个容器同时尝试更新，Git 操作可能因为冲突而失败，应有重试或跳过机制
- **新代码存在破坏性变更**: 编译成功但运行时崩溃，应有健康检查机制来验证新版本是否正常运行

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 在容器启动时自动检查配置的 Git 分支（默认 master）是否有新提交
- **FR-002**: 系统 MUST 支持通过环境变量配置自动更新行为（启用/禁用、分支名称、检查间隔等）
- **FR-003**: 当检测到有新提交时，系统 MUST 自动拉取最新代码、执行编译（如 npm run build）并重启服务
- **FR-004**: 当没有新提交或更新过程失败时，系统 MUST 使用现有代码启动服务，确保服务可用性
- **FR-005**: 系统 MUST 记录所有更新相关的操作日志（检查、拉取、编译、启动、错误等）
- **FR-006**: 系统 SHOULD 支持通过信号或特定端点手动触发更新检查
- **FR-007**: 系统 SHOULD 在更新前创建备份或保留上次成功编译的版本，以便在失败时快速回滚

### Key Entities *(include if feature involves data)*

- **UpdateConfig**: 自动更新配置信息，包括启用状态、目标分支、Git 仓库地址、凭证等
- **UpdateStatus**: 更新状态记录，包括上次检查时间、最新提交哈希、更新历史等
- **BuildArtifact**: 编译产物信息，包括版本标识、编译时间、文件路径、校验和等

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 容器启动后 30 秒内完成更新检查并启动服务（无论是否有更新）
- **SC-002**: 当 master 分支有新提交时，系统在 2 分钟内完成从检测到服务启动的整个更新流程
- **SC-003**: 更新失败的情况下，系统在 10 秒内回退到现有代码并启动服务，可用性达到 99.9%
- **SC-004**: 运维人员可以通过环境变量在 1 分钟内启用或禁用自动更新功能
- **SC-005**: 所有更新相关的操作（检查、拉取、编译、启动、错误）都被记录到日志中，便于故障排查

## Assumptions

- 容器运行环境具有互联网连接能力，可以访问 Git 仓库
- Git 仓库使用标准的 Git 协议（HTTPS 或 SSH），并提供有效的认证凭证
- 项目的编译过程通过 package.json 中定义的脚本（如 build）执行，并且编译成功后会生成可运行的产物
- 容器运行的目标环境支持文件系统操作（拉取代码、写入编译产物）
- 服务的启动命令是确定且可重复的，可以通过统一的入口脚本启动

## Clarifications

### Session 2026-03-31

- **Q**: Git 认证方式应选择哪种实现方案？  
  **A**: 同时支持 HTTPS Token 和 SSH Key 两种方式（选项 C）——HTTPS Token 适合 CI/CD 自动化，SSH Key 适合企业环境，两种方式覆盖绝大多数使用场景
