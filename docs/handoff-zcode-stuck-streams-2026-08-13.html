3. 失败签名与诊断命令

「静默流式失败」的完整识别签名（网关日志视角）：

  1. 认证/路由/转发全部正常（Request authenticated → Anthropic message request → Request routed to plan → Forwarding Anthropic streaming request）；
  2. 上游已发送 ≥1 个数据块（网关已 reply.hijack() 并发出 SSE 头——否则会走 error handler 打出 Request failed，本事件中没有）；
  3. 流中途死亡：无 Anthropic streaming request completed、无 token 回调、无任何 warn/error 错误日志；
  4. 同一毫秒出现 Plan marked as failed（warn，planId=5）——catch 里 router.markPlanFailed() 的痕迹；
  5. 收尾为 Request completed，statusCode: 200、provider: {durationMs: 0, statusCode: 0}、无 tokens——这是 handler 早期 attachProviderMetrics（durationMs 0/statusCode 0）的原值，从未被覆盖。
⚠️ 关键机制：时长 =「流时长 + 300s」的两条请求，与 plan.timeout: 300（秒）精确吻合。makeStreamingRequest 里 timeout: options.timeout * 1000 是 socket 空闲超时——上游停止发数据 300s 后，req.on('timeout') → destroy → handleStreamError('Request timeout') → reject → catch（headers 已发送）→ 静默 logCompletion()。也就是说这两条请求的「卡死 5 分钟」是网关的超时兜底在兜着，而不是自然结束。
